# Hosting: Railway for the API, worker and Postgres; Vercel for the web app

- **Date:** 23 November 2026
- **Status:** Accepted
- **Decided by:** William, in a grilling on 23 Nov 2026
- **Builds on:** `2026-11-18-api-and-jobs.md` (Hono, Postgres, pg-boss; hosting left open), `2026-11-21-publish-job.md`, `2026-11-21-stored-results.md`, `2026-11-23-copy-alert-notifications.md` (hosting comes before the bot)
- **Supersedes in part:** `2026-11-18-frontend.md`, its "publish as a static mirror on DeWEB" requirement (decision 6 below)

## Context

Foreman runs on William's laptop. The API, the index follow and the results refresh need a host that keeps a process running, and judges need one link that works. The follow and refresh scripts were written to run every 5 minutes "once hosting is chosen". pg-boss was chosen on 18 Nov but isn't wired in yet. The local database is 213 MB.

Prices below were checked on 23 Nov 2026, mostly on third-party pages. They are estimates; check the providers' own pricing pages before paying.

## Decisions

1. **A managed platform: Railway.** One Railway project holds three services: the Hono API, a worker, and Postgres. Each deploys from the GitHub repository.
   - **Cost:** Railway's Hobby plan is $5 a month including $5 of usage, and is billed by memory, CPU and disk beyond that. Estimated $10 to $20 a month for Foreman. Hobby caps a volume at 5 GB.
   - **Not chosen:**
     - **Render:** about $21 a month or more. It has no free background worker, and free Postgres is deleted after 30 days.
     - **A VPS:** cheapest, but William would run TLS, backups and updates himself.
     - **Fly.io plus a separate database:** two providers.

2. **The jobs run in a pg-boss worker, its own Railway service.** One schedule every 5 minutes runs, in order:
   1. follow the index;
   2. refresh the results it touched;
   3. publish what changed (decision 4).

   pg-boss never starts a run while one is still going, retries a failed run, and keeps a record of each run in Postgres. pg-boss itself is free; the always-on worker adds about $1 to $3 a month. The Telegram bot joins this worker later (`2026-11-23-copy-alert-notifications.md`, decision 5).
   - **Not chosen:**
     - **Railway cron:** cents a month, but no retries or run record, and overlapping runs need care.
     - **Jobs inside the API:** saves about $1, but a slow follow competes with page requests, and one crash stops both.

3. **Railway's Postgres starts from a dump of the local database.** William runs `pg_dump` locally and restores the dump on Railway; the follow then catches up from where the dump ends. A dump is used rather than a rebuild from the chain because:
   - it takes minutes rather than hours of archive-node reads;
   - it spends none of the archive quota;
   - it keeps `published_results`, the record of the 26,741 testnet publications, so nothing is published twice.

   Everything in it can still be checked against the chain.

4. **The worker publishes to the X Layer testnet on every run, only what changed.** That means results whose hash differs from their last publish, as the publish job already works. A changed verdict is then on chain within minutes of the follow seeing it.
   - **The key:** William chose to use the current publisher, his development wallet `0x2ef2fed3f9b3d5385499008051031320b1fb49ef` (also the contract's deployer). Its key is held as a sealed Railway variable, `PUBLISHER_KEY`. William sets it; no agent session sees it.
   - **The risk, stated in the grilling:** that wallet's key lives on a third-party host. If it leaks, the owner wallet `0xa1a6f73a2443446204fb850effc9452597515ab8` replaces the publisher. Until then, on the testnet, someone could spend its test OKB and publish false results.
   - **Not chosen:** a fresh wallet used only by the host, made publisher by the owner wallet (the recommended option). This is still available later without a new contract.
   - **Testnet only.** Mainnet publishing from the host needs a new decision. The publish job keeps refusing a chain whose results contract isn't deployed.

5. **The web app's main link is on Vercel.** It is the static build, deployed on every push, with a preview link for each push. `VITE_API_URL` points at the Railway API. The API already allows any origin for GET requests (`apps/api/src/server/app.ts`), so it needs no change for Vercel's domain.
   - **Cost:** the Hobby tier is free. Vercel's terms limit it to personal, non-commercial use, so if Foreman takes paying users it moves to Pro, about $20 a month.
   - **Not chosen:** a static service on Railway. It means one provider, but no CDN or preview links.
   - The domains are Railway's and Vercel's own for now.

6. **DeWEB is optional, after hosting.** DeWEB is X Layer's on-chain website hosting.
   - **Its place in the hackathon:** it is not a separate sponsor. The Build X page names it as one way to qualify, which Foreman already meets through TapeOut contracts and X Layer data, and as an example under "Ecosystem Integration", one of the judged criteria.
   - **Cost:** other entries report about 0.09 to 0.1 OKB once to set up a site, mostly the 0.08 OKB container, plus a small storage fee for each upload. All of it is in mainnet OKB from William's own wallet. These figures are unverified.
   - **Reaching it:** reportedly a `tape://` address. Which browsers and wallets open it hasn't been checked.
   - **The plan:** keep the app's static build so a mirror stays possible. Once Railway and Vercel work, research the steps and costs properly; William then decides whether to pay. It goes on the cut list.

7. **Failures show on `GET /health`, and in the logs.** The endpoint reports, with their blocks and how long ago:
   - the last successful follow;
   - the last successful refresh;
   - the last successful publish.

   It says "behind" when 30 minutes pass without one. The worker logs each run: blocks, counts and transaction hashes, never keys. A free uptime checker can watch the endpoint later. Once the bot exists, it can message William too.

## Secrets and who does what

- **On Railway, as sealed variables set by William:**
  - `DATABASE_URL`, from Railway's Postgres;
  - `BNB_ARCHIVE_RPC_URL`, `BNB_RECENT_RPC_URL` and `BNB_ARCHIVE_LOG_BLOCKS`. The last must match the archive node's log limit: left unset, the client reads 10 blocks at a time (Alchemy's free-tier limit). On 23 Nov 2026 `BNB_ARCHIVE_RPC_URL` pointed at NodeReal, which served 50,000-block log reads on 20 Nov;
  - `XLAYER_RPC_URL`;
  - `PUBLISHER_KEY`;
  - later, `TELEGRAM_BOT_TOKEN` and the VAPID private key.
- **On Vercel:** `VITE_API_URL`, and later `VITE_VAPID_PUBLIC_KEY`. Both are public.
- **Accounts and deploys:** William creates the Railway and Vercel accounts, connects the repository, sets the variables, restores the dump and deploys. Agent sessions write the code and configuration: the worker, `/health`, and the build and start commands. They never deploy or handle a key (CLAUDE.md, "What the agent cannot do").

## Consequences

- To build, in order:
  1. the pg-boss worker, using the existing follow, refresh and publish functions;
  2. `GET /health`;
  3. the Railway and Vercel build and start configuration;
  4. dump and restore steps for William.
- The cut list gains the DeWEB mirror, before copy alert notifications.
- **On the RPC quotas:** a follow every 5 minutes stays inside publicnode's 5,000-block window, so it mostly reads publicnode, not the archive node. If the worker stops for long enough to fall behind, catching up uses the archive node's monthly quota.
